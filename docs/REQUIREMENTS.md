# Requirements — remaining features

Derived from the measured legacy corpus and the decisions in [DATA_MODEL.md](DATA_MODEL.md).
Nothing here is aspirational: every requirement traces to either a measured property of the
source data or a principle (P1–P10) already agreed.

## How to read this

Each requirement has an ID, one testable statement, the evidence behind it, and a `Verify:` line.

`Verify:` is one of:

| Form | Meaning |
|---|---|
| `T-<ID>` | an automated test exists and passes |
| `T-<ID> (pending)` | the test is written as `it.todo` and names this requirement |
| `manual: <steps>` | cannot be meaningfully automated; procedure given |

A requirement with no `Verify:` line is not finished, however confident anyone feels about it.

**St (status):** ✅ built and verified · 🟡 partially verified — the enforceable half holds, but a
stated check is still skipped or unbuilt · ⬜ not built

`St` is derived from `Verify:`, and a test asserts the two agree. A row cannot claim ✅ while its
test is still `it.todo`.

## 1. Authentication and session

The legacy app had one shared plaintext password (`tblSystem.Password = 'septic'`) for every
user. It was deliberately not imported. There is therefore no auth history to preserve and no
backwards compatibility to honour.

## 2. Driver PWA — the primary deliverable

Sized from the data, not from taste. 2024: **2,160 jobs over 234 operating days**, median **9/day**
company-wide, p90 **18**, max **30**, across an average of **2.34** active pumpers (max 5). A
driver's day is **~4 stops, peaking near 13**.

That is one scrollable ordered list with large tap targets. It is not a calendar grid, and not a
map-first UI. Any requirement that would push the design toward either is deliberately absent.

| DRV-08 | ✅ | `service_date` is assigned by the **server**, never accepted from the device. The device clock only orders offline notes. | P10. Refused by name rather than ignored: a client sending a date it invented is broken, and silently overwriting it would leave the client broken forever while the ledger disagreed with the screen. | DRV-09 | ✅ | A second service for the same property on the same date is refused with an actionable message, never a 500. | `UNIQUE (property_id, service_date)` holds across all 48,216 legacy rows. | DRV-10 | ✅ | Properties with `reminder_opt_out = true` are visibly marked on the card. | 856 properties. A driver calling a "no reminders" household is a complaint waiting to happen. | DRV-11 | ✅ | County is stored and shown normalised, with the original spelling retrievable. | 34 distinct spellings for 7 counties; `FDL` (26 rows) and `Fond du lac` (6) are aliases of `Fond du Lac` (5,776). 0013 keeps the raw string so this does not rest on the legacy landing zone, and 0015 put both spellings on the dispatch view. 49 properties have no `county_id` at all — 0013 refused to guess which county a municipality sits in, per LED-06, so a card that rendered only the normalised name would show those blank, which reads as missing data rather than as a refusal to invent one. | DRV-12 | 🟡 | Usable with no network after launch: browsing, completing stops, notes and photos all queue locally. | The entire reason it is a PWA. The offline layer is built and tested — `frontend/src/offline/`, plus `StopActions` and `QueueStrip` on the driver's screen. A queue mints `client_uuid` **once, at enqueue**, and never regenerates it, which is what makes DRV-13's server-side dedup reachable at all; it deletes only after the server acknowledges, so a crash between send and delete re-sends the same key instead of losing the row; and it reads a bare status code as one of four verdicts, because 401 and 409 look identical and need opposite handling — an expired login keeps the pump-out and parks the queue, a refusal on the facts discards it and asks for a reload (DRV-14, executed with no merge). `public/sw.js` caches the shell, never intercepts a non-GET, and never caches `/api/auth/` — a cached login response is a bearer token sitting in storage that outlives a logout. 37 frontend assertions, and the end-to-end one takes a tap against a dead radio, watches it queue, restores the radio, and requires the screen to re-read the day rather than assume its own write landed. Three things keep this off ✅. **Deployment, and the largest:** this app is served to handsets on a private network over a VPN, at an address like `http://10.8.0.30`. The endpoint reads the first attempt's row and answers 200 with it; the test sends one uuid three times and requires one row, three successes, and an `arrived_at` that never moved. | `T-DRV-13` ✅ |
| DRV-14 | ✅ | Conflicts resolve by ownership, never by merge: server owns schedule and status, device owns its notes and photos. | No field is concurrently edited by two parties, so no merge logic is ever needed. Keep it that way. The notes endpoint is append-only by construction — no UPDATE, no PATCH, no verb — and two tablets that both typed "lid was cracked" produce two rows by design. | DRV-15 | ✅ | Photos capped at 3,000,000 **total pixels**, enforced server-side on re-decode, not on one edge. | A per-edge cap misses 2000×8000 (16 MP, narrow enough to pass a width check) and rejects a fine 10000×300 panorama. Both halves now asserted: the schema in `verify_schema.sql`, and the pipeline end-to-end — 2000×8000 refused by pixel total (413), exactly 3,000,000 accepted, and the dimensions recorded are the ones `sharp` measured on the stored bytes; a body claiming `width: 1` is not read, which is the requirement's whole point stated as a test. | `T-DRV-15` ✅ schema · `T-DRV-15b` ✅ pipeline |
| DRV-16 | ✅ | Photo EXIF is stripped by default; GPS stored only on explicit opt-in at capture. | P8: **zero** coordinates exist in the source. Warehousing a driver's GPS track at every stop is a liability nobody asked for. The strip is re-encoding, not scrubbing — there is no scrubber step to forget. The proof uploads a JPEG carrying a hand-built EXIF/GPS APP1 segment and reads the stored bytes back from object storage: no APP1, no EXIF, and the row's `gps_lat`/`gps_lng` stay NULL even though the file held them. Coordinates without the flag are discarded, observably: the response and the row both say nothing was kept. | `T-DRV-16` ✅ |
| DRV-17 | ✅ | Image bytes live in object storage; the database stores metadata only. | P9. A `bytea` column pushes multi-megabyte payloads through the ORM, the pool, every `SELECT`, and every backup. | `T-DRV-17` ✅ |

| DRV-19 | ⬜ | The app installs to the home screen and launches fullscreen. | If it opens in a Safari tab bar it will be closed, and the paper clipboard wins. | manual: install on Android + iOS, confirm standalone display mode |
| DRV-21 | ✅ | A driver (or the office) can **file a service record from the site record** — work that happened without ever being on a route. | The route is the plan; the truck finds the work. The answer is a work queue, not a form: `GET /api/ledger/unbilled-events` reads the **heads** of correction chains (a superseded event is history with a reason — billing it would bill the same truck twice), keeps only `completed` rows inside the window, and refuses nothing: an event is on the list exactly while `invoice_lines` has no row naming it. When an invoice line is attached — from the bid path, an adjustment, or a hand-fix in the database — the event leaves the list by the same logic it entered. The window is the office's dial (default 60 days, `days=all` for the archaeology); `business_today()` travels in the meta so the page can say how long the oldest unbilled job has been waiting. Sorting is per column (date, cust #, site, payer), because the two real workflows are *work the newest* and *work this customer*. | `T-BIL-19` ✅ |
| BIL-20 | ✅ | The office can **create an invoice** — from the billing queue or from the invoice desk — and every line must name the thing it charges for. | BIL-19 explained why nobody could bill a pump-out: the price book was a fiction and a blank form would have been guessing. The answer is not a guessed price list; it is that *the office types the price line by line, next to the work*. `POST /api/invoices` accepts an addressee and lines, and each line must reference **exactly one** lawful thing: a completed, unbilled service event (`0033` adds the fourth reference, `bid_item_id`, so a price-list line names its item the way a bid line does — the BIL-01 doctrine extended, not relaxed), or a price-list item, or a legacy product code. The server owns every number: line amounts are `ROUND(quantity × unit_price, 2)` recomputed in SQL (BIL-04 — the client cannot send a total, only the quantity and price it believes, and the response shows what the database believes), tax is the settings rate stamped at creation and **zero for a payer marked tax-exempt** (SCH's `tax_exempt` finally answers to something), and the header totals are derived from the lines, not trusted from the browser. A line may also be taken off the rate: `taxable` on the line (0034, default true) is intent the office sets, the flag is stored, and the rate is measured over the taxable lines only — `round(taxable × rate, 2)` in SQL, never from the browser. Refusals name the next thing needed: billing an event that is already billed returns the invoice number that billed it (409, and the same transaction locks the events first, so the second of two clerks who both click Create gets the 409, never a second invoice); billing a superseded event names the correction that is now the head; a line with two references is refused as contradictory, because a line that bills one truck twice is exactly the bug the correction chain exists to prevent. Draining the queue needs no drain button: the queue's membership is a query, and the moment the invoice's line names an event the row answers false — creation and draining are the same fact seen twice. The queue page preselects lines from checked rows and the payer from their site's current owner; the invoice desk opens the same dialog blank. | `T-BIL-20` ✅ |

## 9. Traceability

The executable list lives in `septic-app/backend/tests/`. `npm test` prints the
`it.todo` entries, so **the test output is the build checklist** — a pending requirement is visible
in CI rather than buried in this document.

Counts below are **asserted by a test**, not maintained by hand. The table drifted once while it
was prose, which is why it is now checked against the parsed requirement rows on every run.

| | Count |
|---|---|
| Requirements | 95 |
| ✅ built and verified | 90 |
| 🟡 partially verified | 1 |
| ⬜ not built | 4 |
| Pending, tracked as `it.todo` | 0 |
| Manual procedure only | 7 |

Jest's own totals move every run, so they are not asserted here — but the `it.todo` count above is
kept equal to the pending list by construction, and the `⬜` count cannot exceed it by more than the
manual rows. There are no `skip`ped tests: the last one was `SCH-01`'s behavioural form, which was
rewritten to insert its own row inside a rolled-back transaction and now runs every time.

### Documentation is one of the things under test

`tests/repo-hygiene.test.ts` parses `src/routes/` and `package.json` and asserts that
`backend/README.md` agrees with them: every mounted route is written down, no route is advertised
that is not mounted, every `npm` command inside a code block names a script that exists, and the
entity count the README states is the count `@Entity` appears. Four assertions, all four
mutation-tested.

That file exists because its previous revision had become fiction — it told people to run
`npm run migration:run`, gave passwords for accounts that were never seeded, listed eleven tables as
the schema when eight of them had been deliberately deleted, and named 5 of the 24 routes. The
failure mode is quiet: a README stays
plausible while the code moves away from it, so review does not catch it and a newcomer finds out by
following it.

Two limits worth knowing. It only checks **commands in fenced blocks** — prose is allowed to name a
removed script, and the README does exactly that to warn about it. And it can only see the backend
tree, so the repository root's `README.md` and `docs/` are outside its reach; those are checked for
secrets by `scripts/audit-secrets.sh` and for requirement counts by `requirements.todo.test.ts`, but
nothing yet verifies their prose. Numbers in those two files are written as measurements taken on a
date, with the query that recomputes them, because that is the one way a figure can stay honest
without someone re-reading it.

**If you mutation-test this file, restart the backend afterwards.** The dev server watches
`src/routes/` and respawns, so a temporary route rename leaves it serving the renamed path. Restoring
the source does not always retrigger the watcher, and the next `dispatch-api.test.ts` run then reports
fifteen unrelated `404` failures that look like a data problem and are a stale process.

The backend suite runs one file at a time (`maxWorkers: 1`), and that is a correctness setting
rather than a tuning one. Several files need a property not already booked on today's route, find
it with a `SELECT … WHERE NOT EXISTS`, and then insert it in a second statement; under parallel
workers two files pick the same site in that gap and one loses to `uq_stop_one_open_route`. Three
runs measured 2 failures, 0 failures and 16 failures on identical code. It had been accepted as a
flake in one named file, which was the wrong conclusion — the failure lands wherever the race
happens to be lost. Serialising costs roughly twenty seconds and the runs are now repeatable.

### Running it

```bash
# inside the backend container
npm test                      # 17 suites — 254 passing, 15 todo (measured 2026-08-31)
npm test -- tests/auth.test.ts

# on the host — needs git, so it cannot run in the container
./scripts/audit-secrets.sh

# in the frontend container — the offline queue and the driver's cards (T-DRV-12)
cd frontend && npm test
```

The suite needs the stack up (`docker compose up -d`) and a seeded user, because `media-cap.test.ts`
inserts real rows inside a transaction it then rolls back, and `auth.test.ts` calls the live server.
Test users are created under `@test.invalid` (a reserved TLD) and deleted in `afterAll`.

The frontend suite is separate and smaller: 4 files, 54 assertions, covering the offline queue, the
capability check, the driver's action buttons and one end-to-end dispatch render. It runs in the
frontend container because that is where its jsdom and its React live.
